# Spike 5 matrix — script list and sampling rationale

Each script runs twice via the compiled `cmd/go` test binary
(`TestScript/<name>`): once stock (no GOFLAGS), once with
`GOFLAGS=-toolexec=<wrapper>`. A script "passes" in a mode iff the txtar
script's own assertions (stdout/stderr/exit-code/file-content) hold — so
equal pass/fail across modes means identical observable behavior by the
suite's own definition. Divergence = pass in one mode, fail in the other.

## Sampling rationale

The seam under test is `-toolexec`: every `compile`/`asm`/`cgo`/`link`/
`cover`/`vet`/`preprofile` tool invocation is prefixed with the wrapper
argv (verified in source: work/build.go:354, work/gc.go:136,332,676,724,
work/exec.go:1490,3088,3337, work/cover.go:26, work/action.go:496).
Sampling maximizes seam coverage per script:

1. SEAM-DIRECT: scripts that assert on -toolexec behavior itself.
2. TOOL-COVERAGE: at least one script per wrapped tool
   (compile, asm, link, cgo, cover, vet, preprofile/PGO).
3. CACHE/METADATA-BLINDSPOTS: scripts where the wrapper sees nothing or
   only probes (build cache hits, two-level test cache, staleness) — the
   wrapper cannot observe or influence driver-side caching; behavior must
   still match.
4. KNOWN-RISK (T3): cgo/gcc boundary (gcc is NOT wrapped — exec.go
   ccompile), test JSON protocol, response files (@file argv),
   GOFLAGS composition, buildvcs stamping, PGO.
5. COMMAND-COVERAGE: build, run, test, vet, list, env, mod all represented.
