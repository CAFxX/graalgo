## Findings

### P1-1. Finalizers silently never run (and objects leak) unless the program calls `runtime.GC()` — missing from DIVERGENCES.md

`GcInterop.setFinalizer` pins every finalized `GoPointer` in the static
`PINNED` set (strong references), and only `gc()` clears it:

- `phases/phase2/src/main/java/graalgo/runtime/GcInterop.java` — `PINNED`
  field javadoc: "the registration keeps the GoPointer alive until the
  program either cancels (SetFinalizer(x, nil)) or calls runtime.GC()";
  `gc()` does `PINNED.clear()` then `System.gc()`.

As long as `PINNED` holds the object, the shared `Cleaner`'s phantom can
never clear, so the finalizer action can never run. Consequence: a Go
program that calls `runtime.SetFinalizer(x, f)`, drops `x`, and never
calls `runtime.GC()` sees `f` **never run** and `x` retained **forever**
(`PINNED` grows unboundedly — a genuine memory leak). In gc, finalizers
run when the object becomes unreachable; no explicit GC call is needed.

The mechanism is described in the `PINNED` field's code javadoc, but
`phases/phase2/DIVERGENCES.md` — the canonical divergence registry —
has **no entry** for it (DIV-M4-1…DIV-M4-9 cover the nil argument, the JVM
thread, the GC approximation, memstats, weak.Pointer, unsafe.Pointer,
SetFinalizer-on-nil, pprof, FreeOSMemory — not this). A reader of the
registry, or of the class javadoc's "after release, lifetimes are natural
(tied to Go variables)", would not learn that finalization is gated on an
explicit `runtime.GC()`.

**Falsifying test:** register finalizers on N dropped objects, do *not*
call `runtime.GC()`, force JVM GC via allocation pressure, assert all N
finalizers ran → fails (0 run). Additionally assert `PINNED` is empty
after the objects become unreachable → fails (still N).

**Remediation:** add a DIV-M4 entry stating the gating and the leak, or
change the design (e.g. pin only across the register/cancel window via a
per-object reachability fence at the Go call sites rather than a global
set drained by explicit GC).

### P2-1. `Scheduler.park` javadoc contradicts `SchedulerCore.parkCurrent` on the wake-action thread

- `phases/phase2/src/main/java/graalgo/runtime/Scheduler.java:50-53`:
  "`wake` runs on the **waker thread** before re-admission."
- `phases/phase2/src/main/java/graalgo/sched/SchedulerCore.java:252-258`:
  "`onWake` runs on the **goroutine's own vthread** immediately after
  resume (before `parkCurrent` returns)."

The code is unambiguous (`SchedulerCore.parkCurrent`, lines ~300-306):
`awaitAck(h, t)` returns on the parking vthread, then
`h.wakeAction.getAndSet(null)` and `action.run()` execute on that same
thread. The `Scheduler.park` doc is wrong. A caller relying on
waker-thread semantics (e.g. doing non-vthread-safe work in `wake`) would
be misled. Fix the `Scheduler.park` javadoc to match the code.

### P2-2. `JfrEventsTest.testHotLoopParkFilter` comment misdescribes the sampling phase (off by one)

`phases/phase2/src/test/java/graalgo/jfr/JfrEventsTest.java:353-356`
says "seq 1024/2048/3072/4096 hit the 1-in-1024 mask". But
`JfrEvents.parkResumed` evaluates `(h.parkSeq.get() & 1023)` *after*
`armPark` already incremented `parkSeq` past the park's generation, so
the sampled generations are actually 1023/2047/3071/4095. The test still
passes (4 per goroutine either way; the generous 12–20 bound absorbs it)
and `EVENTS.md`'s "deterministic via parkSeq" claim holds — the rate is a
true 1-in-1024. Only the comment's mental model is off by one. Worth
fixing so the next reader doesn't "correct" the code to match the
comment.

### P2-3. `GoOnce` winner path can strand waiters on contract violation

`phases/phase2/src/main/java/graalgo/runtime/sync/GoOnce.java:44-52`:
the CAS winner runs the action, then inside `synchronized (waitLock)`
does `state.set(DONE)` and *then* `SchedulerCore.current()` before
draining waiters. If the winner is not a scheduler goroutine,
`current()` throws `IllegalStateException` — with `state == DONE` but
waiters never unparked: every parked waiter hangs forever, and the
throw masks as an internal error. The class documents "must be called
from a goroutine", and the fast path is safe from any thread, so this
needs a contract violation to trigger — but the failure mode (silent
hang of *other* goroutines) is disproportionate. Hoist
`SchedulerCore.current()` above the state transition or drain waiters in
a `finally`.

### P2-4. `GoroutineHandle.armed` is write-only dead state

Set in `SchedulerCore.armPark` (`SchedulerCore.java:226`), never read by
production code (only by `SchedulerCoreTest` assertions). The spike-2b
external-waker protocol was never implemented; all wakeups route through
the drainer. The model-check report (§7) already admits this. Remove it
or document it as intentionally retained for tests — dead concurrency
state invites a future reader to build on a protocol that doesn't exist.

## The three hardest attacks attempted (all failed)

**Attack 1 — spurious wakeup on a plain channel op.** `GoChan.recv()`
reads `w.value`/`w.ok` unconditionally after `parkCurrent`; a spurious
wakeup would return a bogus `(null, false)`, and `send()` would return
without delivering. So the code *assumes* no spurious wakeup — I tried to
produce one via a stale `unparkPending` entry. I enumerated every
`unpark` source: channel handoff (`deliverToReceiver`/`takeFromSender`),
`close()`, all four sync primitives, timer SLEEP fire, select-claim wins.
Every one dequeues the waiter under the relevant monitor *before*
unparking, and every enqueued waiter parks unconditionally afterwards
(verified in `GoChan.send`/`recv`, all three `SelectOp` park sites, all
sync `parkCurrent(null)` sites, `Timers.sleep`). Monitor serialization
means each waiter is dequeued+unparked exactly once; the select's shared
CAS claim (P0-1) means at most one waker wins per select. No stale unpark
is reachable, so the 1:1 park/unpark pairing holds and the no-spurious-
wakeup assumption is sound. (The model checker's "spurious tolerated" is
a conservative over-approximation of the real pairing.)

**Attack 2 — lost claim / result overwrite in the select block-phase
sweep.** Target: the `immediate` path — waiter enqueued on channel A,
self-claim won and completion succeeds on channel B, select returns
*without parking* while a waker on A unparks it (lost unpark → the
drainer stashes it; later park consumes it spuriously — or worse, two
wakers both claim). The load-bearing property is P0-1: `tryClaimSelf()`
precedes `completeUnderLock`, and the self-claim is held across the
completion. Interleaving: S enqueues on A (claim released), then wins
self-claim on B and completes under B's monitor. A concurrent sender on A
dequeues S's waiter and calls `accept()` → CAS vs `SELF_CLAIM` fails →
waiter dropped, no unpark. `cleanup(mine)` then removes the (already
gone) entry. For the `claimedByOther` path, the winner's UNPARK is always
in flight before S parks, and the drainer's stash absorbs either order.
I could not construct an interleaving where a select both returns
`immediate` and receives an unpark, nor one where two wakers both win the
claim. `SelectOp` is single-use (`ChanOps.selectGo` creates, calls
`execute()` once), so the never-released `SELF_CLAIM` on the `immediate`
path is harmless.

**Attack 3 — timer Stop/Reset racing fire (stale send, lost tick, double
fire).** Target: the pop → `stillCurrent` → `trySend` → ticker re-arm
sequence in `TimerHeap.timerLoop`/`fireChanLocked` vs concurrent
`stopChan`/`resetChan`. The timer thread holds the heap lock across the
*entire* `fireChanLocked` (pop and `byId.remove` happen under the same
hold), and stop/reset must acquire the heap lock — so they serialize
strictly before or after the fire. Before: entry cancelled, or
`stillCurrent(id, generation)` fails under the heap→owner lock order (id
cleared / generation bumped) → no send. After: the tick was already
`trySend`'n into the 1-buffered channel, and stop/reset's unconditional
`drainLocked` reaps it — Go 1.23+ parity (drained stale value counts as
active, returns true). The ticker re-arm reuses the same (id, generation)
but is atomic under the heap lock, so no reset can slip between fire and
re-arm. Lock order heap → owner → chan is consistent everywhere; no
path takes them in reverse (channel/select code never acquires heap/owner
locks). The stale-send race is closed structurally, stronger than gc's
seq/sendLock protocol — as the code comments claim.

## Notes (non-findings, for the record)

- `Drainer`'s `unparkPending` retention for exited/never-parking handles
  is bounded (handle ids from a monotonic `AtomicLong`, never reused) —
  the model-check report's claim verified in `GoroutineHandle`.
- `awaitQuiescence`'s no-concurrent-spawn contract is documented and the
  increment/decrement pairing is race-free (the vthread cannot reach its
  `finally` before the spawner's increment + INIT offer).
- `SchedulerCore.install(null)`-style teardown and `pollCurrentThread`
  no-handle no-op preserve Phase-1 scheduler-less behavior.
- The `emitQuietly` swallow is scoped to `RuntimeException` (Errors
  propagate) — appropriate for scheduler-critical hooks.
- `GoTimer`'s documented P2-1 divergence (1-buffered vs gc-unbuffered
  timer channel, `len(t.C)` observable) is accepted for Phase 2 with a
  Phase-3 re-test trigger — noted, not a finding.
