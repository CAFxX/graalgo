# T6 — Optimization Inventory: what Graal/Truffle compilation actually gives beyond Go's gc toolchain

Track: graalgo research · T6 (optimization inventory)
Date: 2026-10-03 · Author: T6 subagent
Sources: [P1] = primary (GraalVM/Oracle docs, oracle/graal repo, Go 1.27.1 source at ~/tools/go, openjdk/valhalla-docs), [S] = secondary, clearly labeled.
Method rule honored: every claimed advantage names its falsifying benchmark; speculation is labeled [SPECULATIVE].

**Framing honesty, up front.** Graal's most famous tricks — speculative type specialization, inline caches, deoptimization — exist largely to *recover at runtime the static type information that Go already has at compile time*. Go is statically typed; its dynamism lives almost entirely at interface boundaries and in `reflect`. So the biggest Graal brochure claims shrink on contact with Go semantics. The real, defensible wins are narrower: (1) partial escape analysis past gc's flow-insensitive EA, (2) loop auto-vectorization, which gc essentially lacks, (3) profile-driven inlining *without* a separate PGO training run, and (4) the Truffle-specific ability to specialize interpreter-level dispatch (interface calls via inline caches) with deopt fallback. Everything else is either already done well by gc or [SPECULATIVE].

## 1. Speculative inlining + deoptimization across package boundaries

**Mechanism (Graal/Truffle).** Graal inlines aggressively — its priority inliner (default since GraalVM 25.3, GR-77137 [P1: oracle/graal compiler/CHANGELOG.md]) simulates the *benefit* of inlining rather than deciding on bytecode size alone [P1: Oracle Labs GraalVM page]. Speculation means it can inline based on *runtime-observed* facts (receiver types at interface call sites, branch probabilities, constant arguments) and plant a guard + deoptimization point: if the assumption breaks, execution falls back to the interpreter and recompiles [P1: PLDI 2017 Graal tutorial slides]. On Truffle, this is per-AST: a call node that has only ever seen one function type compiles to a direct call; a new type triggers deopt and re-specialization. Package/module boundaries are irrelevant — profiling is whole-program at runtime.

**gc status (what it already does well).** Do not undersell gc here:
1. Mid-stack inlining since Go 1.12 — gc inlines *through* call chains, not just leaves (budget: `inlineMaxBudget = 80` nodes, `~/tools/go/src/cmd/compile/internal/inline/inl.go` [P1]).
2. PGO since Go 1.20 raises inline budgets for hot functions (`inlineHotMaxBudget`, hot-node budget boost in `inlineBudget`) [P1: inl.go].
3. Static + profile-guided devirtualization of interface calls (`cmd/compile/internal/devirtualize`: static devirtualization where the concrete callee is provable, PGO devirtualization emitting a hot-path direct call + fallback) [P1].
4. Cross-package inlining works on exported function bodies shipped in export data — "package boundary" is already not a barrier for gc's inliner in the common case.

**Where Graal could still win.** Cases gc cannot resolve statically: interface call sites with 2–5 receiver types varying *per call site over time*, and call sites whose hot receiver differs between runs (gc's PGO profile is one frozen training run; Graal re-profiles continuously). Truffle inline caches specialize per observed type with deopt on unseen types — no recompilation workflow needed.

**Where Graal would NOT win.** Monomorphic direct calls, leaf functions, and anything gc's 80-node budget already inlines — which is most Go code. Inlining is a solved problem in gc for the common case; Graal's edge is the long tail of megamorphic-ish interface dispatch.

**Falsifying benchmark.** `bench_dispatch`: a loop calling an interface method on a slice of 3 concrete types (a) with fixed 90/9/1% mix, (b) with the mix *changing* mid-run (first half type A dominant, second half type B dominant). Metric: ns/op steady-state for (a); time-to-recover-peak for (b). Setup: graalgo JIT vs `go 1.27 test -bench` with and without `-pgo` (PGO profile collected on phase-a-only input, to punish the frozen profile). Claim "Graal beats gc on interface dispatch" is FALSE if gc+PGO(a) ≥ graalgo-JIT(a) and gc recovers within 2× of graalgo on (b).

## 2. Partial-evaluation-driven escape analysis (PEA) and scalar replacement

**Mechanism.** Graal's *partial* escape analysis doesn't just prove "never escapes → stack allocate"; it can *delay/sink* the allocation into cold branches, and scalar-replace objects field-by-field so only escaping fields are materialized [P1: Oracle Labs GraalVM page: "sinking allocations into less frequently executed branches"]. Because it runs on the partially-evaluated Truffle AST *after* inlining and speculation, it sees through layers gc's EA cannot cross: e.g., a `Point{...}` built inside a helper, passed through two inlined calls, used only on an error path.

**gc status.** gc's EA is genuinely good but structurally limited — its own source says so: "Every Go language construct is lowered into this representation, *generally without sensitivity to flow, path, or context; and without distinguishing elements within a compound variable*" [P1: ~/tools/go/src/cmd/compile/internal/escape/escape.go]. Interprocedural reasoning is only via parameter tags at static call sites. Concrete gc failures where PEA would win:
1. `if err != nil { return fmt.Errorf("wrapping %w", err) }` — allocation on the cold path still heap-allocates the args/frame state in gc; PEA sinks it into the branch.
2. Builder/accumulator patterns: `var b strings.Builder; b.WriteString(...); use(b.String())` — gc heap-allocates the builder's internal slice in many shapes; PEA after inlining can scalar-replace the buffer for small, bounded writes. (Note: `strings.Builder` already has some gc-internal cooperation; the win is for *user* builders.)
3. Small closures capturing loop variables that gc conservatively heap-allocates: `go func() { use(x) }()` patterns where the closure doesn't actually escape the iteration.

**Where PEA would NOT win.** Any object that genuinely escapes to the heap (stored in a map, returned, sent on a channel) — PEA can't help; allocation is allocation. Also: gc already stack-allocates the easy cases, so the delta is only on the *partial* cases above, typically single-digit-percent on allocation-heavy code, not order-of-magnitude.

**Falsifying benchmark.** `bench_alloc_shapes`: (a) error-wrapping hot path (`allocs/op` via `testing.AllocsPerRun`), (b) user-defined builder with bounded writes, (c) closure-per-iteration loop. Metric: allocs/op and ns/op. Setup: graalgo JIT vs `go 1.27 -gcflags=-m` baseline. Claim is FALSE if graalgo's allocs/op ≥ gc's on all three shapes.

## 3. Auto-vectorization

**Mechanism.** GraalVM 25.3 added loop vectorization (GR-28213): "for certain loops doing arithmetic over arrays… transformed into SIMD form… enabled by default, `-Djdk.graal.VectorizeLoops=false`" [P1: oracle/graal compiler/CHANGELOG.md]. This is classic loop auto-vectorization on counted loops over arrays, plus the (incubating) Vector API (JEP 537, 12th incubator in JDK 27 [S: JetBrains blog]) for explicit vector code.

**gc status — the honest gap.** gc has *almost no* auto-vectorization: no loop vectorizer in the SSA backend; SIMD appears only via hand-written assembly/intrinsics in the standard library and runtime. This is the single largest *structural* optimization gap in the inventory. Caveats that shrink it: (1) Go's slice bounds checks and non-aliasing-proof memory model make auto-vectorization legally harder than in Java; a Go frontend on Truffle must still prove no aliasing/bounds escape — the same proofs gc would need; (2) Graal's vectorizer covers "certain loops" (simple counted arithmetic loops) — it is not a general SLP vectorizer; (3) much numeric Go code already calls into assembly-backed stdlib (e.g., `math`, `crypto`) where gc is fine.

**Falsifying benchmark.** `bench_simd`: saxpy (`y[i] = a*x[i] + y[i]`), dot product, and byte-histogram over 1 MiB slices, `-gcflags=-B` not needed (no equivalent to disable in gc). Metric: GB/s. Setup: graalgo JIT vs go 1.27; also vs go 1.27 calling hand-rolled `golang.org/x/sys`-style SIMD where applicable. Claim "graalgo vectorizes what gc cannot" is FALSE if graalgo's GB/s ≤ 1.2× gc on all three (i.e., within noise of scalar code).

## 4. Lock elision / lock coarsening

**Mechanism.** On the JVM, escape analysis enables lock elision (a monitor on a non-escaping object is removed) and coarsening (adjacent synchronized regions merged); biased locking is long gone (removed JDK 18+), so uncontended CAS is the baseline cost being attacked.

**gc status / relevance check — mostly NOT relevant.** Go hot paths rarely use locks the way Java does: channels, `sync.Mutex` in coarse places, and lock-free atomics dominate. gc has no lock elision because Go has no re-entrant monitors to elide — a `sync.Mutex` is a library type wrapping runtime semaphores, and its fast path is already a couple of atomic ops. The only plausible win: PEA proving a `sync.Mutex` (or a struct containing one) never escapes and never actually contends, allowing the frontend to strip the lock entirely — but a mutex that provably never contends and never escapes is a mutex the programmer shouldn't have written. Verdict: include for completeness, expect ~zero measurable delta on real Go workloads.

**Falsifying benchmark.** `bench_mutex`: uncontended `mu.Lock(); x++; mu.Unlock()` in a tight loop, plus a variant where the mutex is embedded in a non-escaping struct. Metric: ns/op. Setup: graalgo JIT vs go 1.27. Claim is FALSE (as expected) if delta < 5% — record it as a *negative* result; do not let it be cited as a win.

## 5. Project Valhalla value types for small Go aggregates — 2026 status check

**Status as of 2026-10-03 (checked, not from training data).** JEP 401 (Value Classes and Objects) was integrated into mainline OpenJDK in August 2026 and ships as a *preview* in JDK 28 EA builds [P1: openjdk/valhalla-docs site, "What's New? August 2026"]. One secondary source (a project's ADR) claims preview in Java 25 with finalization in 26/27 — that contradicts the project site and is treated as stale [S, distrusted]. Current model: value classes give up *identity*, not nullability (`Point p = null` is still legal); flattened, null-restricted storage is a *separate, later* feature set [P1: valhalla-docs "five distinct feature sets"; S: dev.to explainer]. So as of today: no production Valhalla, no dense array layouts yet.

**Mechanism if it existed.** Heap-resident flattening: `Point[]` stored inline (like C structs) instead of pointer-per-element. Go slices of small structs (`[]Point{x,y int}`) are exactly the shape that would benefit — gc today allocates each element inline in the slice backing array *already* (Go slices are value arrays!), so the win vs gc is much smaller than the win vs Java. The real Valhalla-for-Go win would be: (a) value objects as map keys / interface values without boxing+heap allocation, and (b) *generic* flattening the Go compiler can't do (e.g., `[]interface{Point}`-ish shapes via type parameters).

**Adversarial note.** Go's value semantics already give it what Valhalla gives Java. Mapping Go structs to Valhalla value classes buys little over what scalar replacement + PEA already do for non-escaping aggregates, and Valhalla isn't production anyway. This is a 2028+ option, not a 2026 argument.

**Falsifying benchmark [SPECULATIVE].** `bench_flat`: `[]Pair` (two-int struct) reductions and a `map[Pair]int` build, run on a JDK with finalized Valhalla (whenever that exists) vs go 1.27. Claim FALSE if graalgo+Valhalla ≤ gc within 10%. Until Valhalla finalizes, this entire subsection is non-actionable — do not cite it in feasibility conclusions.

## 6. Profile-guided branch layout, loop transforms, misc.

**Mechanism.** Graal does loop peeling/rotation/unrolling, path duplication (`OptDuplication`, enterprise), speculative guard movement, read elimination, and block layout from runtime profiles — standard modern JIT fare [P1: oracle/graal CHANGELOG, GraalVM options docs].

**gc status.** gc's SSA backend does loop rotation/unrolling (limited), bounds-check elimination via `prove.go` + `checkbce.go`/`loopbce.go` [P1: ~/tools/go/src/cmd/compile/internal/ssa], and decent block layout; its register allocator is a capable linear-scan SSA allocator that is rarely the bottleneck on amd64/arm64. gc's weakness is *profile use*: without `-pgo`, branch layout is heuristic; with PGO (1.20+) much of this closes.

**Net assessment.** Against gc *without* PGO, Graal's always-on runtime profiling is a genuine, across-the-board few-percent win on branchy code. Against gc *with* a good PGO profile, the delta shrinks to whatever continuous re-profiling buys (see §1's phase-change benchmark). Do not benchmark graalgo-JIT against gc-without-PGO and call the delta a "Graal advantage" — that's a profiling advantage, and gc can have it too for the price of a training run.

**Falsifying benchmark.** `bench_branchy`: interpreter-style switch-heavy dispatch loop with skewed case frequencies. Metric: ns/op. Three-way: graalgo JIT vs go 1.27 vs go 1.27 `-pgo` (profile from same input). Claim "Graal's profiling beats gc's" is FALSE if go+PGO ≥ graalgo.

## 7. Workload verdicts: beat / match / lose

Numbered per standing preference:

1. **Plausibly BEAT gc:** (a) numeric loops over slices where auto-vectorization fires (§3); (b) interface-dispatch-heavy code with shifting type mixes (§1, phase-change); (c) allocation-churny code with partial-escape shapes (§2) — expect 5–25% on microbenchmarks, low single digits on large apps. All [SPECULATIVE] until the falsifying benchmarks above are run.
2. **MATCH gc:** straight-line integer/float code, direct calls, bounds-check-heavy slice code (gc's BCE is excellent), well-PGO'd servers. Expect noise-level deltas; the JIT's profiling edge mostly cancels against gc+PGO.
3. **LOSE to gc:** (a) **startup/warmup** — Truffle starts in the interpreter; methods compile after thousands of invocations and full Graal compilation of a hot method costs milliseconds-to-tens-of-ms; a CLI that runs 50 ms under gc can take seconds to warm under Truffle [S: general Truffle behavior; quantify per-benchmark, not from memory]. (b) **memory footprint** — JVM heap + code cache + Truffle ASTs vs a static Go binary; expect 10–100× RSS on small programs [SPECULATIVE — falsify with `/usr/bin/time -v` RSS comparison on hello-world and on a small HTTP server]. (c) **latency tail** — deopt storms and GC pauses (G1/ZGC vs Go's low-latency GC) on allocation-heavy request paths. (d) **cgo/assembly-heavy code** — any path through the FFI boundary pays interop tax Truffle can't optimize away.
4. **The meta-point:** gc optimizes the *language as written* (static types, value semantics) with a fast compile; Graal recovers what dynamic languages lack. Go is the wrong language to maximize Graal's brochure — the honest pitch is narrower: vectorization + always-on profiling + PEA long tail, at the price of warmup, footprint, and toolchain complexity.

## 8. GraalVM Native Image AOT: what survives

Native Image AOT-compiles with the same Graal compiler, so *static* optimizations survive: inlining (with the closed-world whole-program view — actually *better* informed than JIT for monomorphic calls), PEA, BCE-equivalents, loop transforms, and the 25.3 loop vectorizer [P1: GraalVM docs; oracle/graal CHANGELOG]. What does **not** survive: speculation without evidence — no deoptimization of AOT-compiled methods, no adaptive re-profiling. The mitigations, all verified [P1]:

1. **PGO for Native Image exists and is the sanctioned replacement for runtime profiling**: `--pgo-instrument` → run → `--pgo=<profile>.iprof` bakes branch/inlining profiles into the AOT build [P1: graalvm.org PGO docs]. Caveat: it is **not available in GraalVM Community Edition** (Oracle GraalVM only) — a licensing/availability constraint on the "drop-in" story.
2. **Truffle runtime compilation inside a native image is real and shipping**: the optimizing Truffle runtime can be embedded in a Native Image; guest code then compiles at runtime *with* speculation and deoptimization (demonstrated Sept 2026 by the Protos project: "native executable with Truffle guest compilation" [S]; deopt-in-native-image mechanics documented in a JKU master's thesis [S]). This is the existence proof for the hybrid mode — but note what it is: the *guest language AST interpreter* compiles at runtime; AOT-compiled *host* methods still don't deoptimize.
3. **Closed-world constraint**: "all classes and all bytecodes reachable at run time must be known at build time" [P1: Oracle Native Image docs]; reflection/JNI/dynamic loading need explicit configuration. For a Go frontend this maps to: the Go package set, `reflect`-reachable symbols, and cgo boundaries must be closed at image-build time — a build-time burden gc never imposes.

Net: pure-AOT graalgo ≈ gc-with-PGO-plus-vectorization on peak throughput for closed-world programs, minus speculation adaptivity, plus Native Image build times (minutes) and config burden. The "advanced optimizations NOT in gc" claim survives AOT mostly as: vectorization + whole-program PEA + PGO-driven layout — i.e., things gc could also do with PGO except vectorization.

## 9. APPENDIX — Hybrid mode: in-image runtime compilation (user requirement 2026-10-03; framing corrected)

**Correction (2026-10-03):** the previous draft framed hybrid as "HotSpot-style tiered compilation" (AOT baseline tier + separate JIT tier). That framing is wrong and is replaced here. The corrected design, per the user's requirement: **the application code AND the JIT compiler itself — the Graal compiler + Truffle partial evaluator + optimizing runtime — are AOT-compiled into the binary; at runtime, that embedded JIT further optimizes hot code.** This is the real, shipping GraalVM capability: Truffle languages on SubstrateVM / Native Image with runtime compilation support. There is no "JIT tier" separate from an "AOT tier" taking over each other's methods — there is one compiler, resident in the image, compiling guest code at run time.

**Architecture mapping for graalgo.** The Go program is *guest* code (Truffle ASTs produced by the Go frontend); the *host* is the interpreter + Go runtime, AOT-compiled into the image along with the compiler itself. At run time, guest code starts interpreted; hot roots are partially evaluated and compiled by the embedded compiler, with speculation and deoptimization back to the interpreter.

**Support status — verified [P1] unless noted:**
1. Runtime compilation inside a Native Image is real and shipping. During closed-world analysis Native Image computes "all methods that are reachable for runtime compilation" [P1: oracle/graal truffle/docs/HostCompilation.md]; the build output reports "Runtime Compiled Methods… only shown if runtime compilation is built into the executable, for example, when building a Truffle language. Runtime-compiled methods account for graph encodings in the heap" [P1: oracle/graal docs/reference-manual/native-image/BuildOutput.md].
2. Independent existence proof, Sept 2026: the Protos project built a native executable that "retain[s] the Truffle optimizing runtime" and validated working guest compilation (both Bytecode-DSL roots reached Tier 2 under forced compilation, OPT_FAILED=0) [S: protos 2026-09-26 announcement — a validated capability, explicitly not a performance benchmark].
3. It is the default, not opt-in, for shipped Truffle native launchers: a GraalVM 25.0.2 CE native image running GraalJS emits AVX-512 *during Truffle compilation at run time*; setting `engine.Compilation=false` removes the behavior [S: oracle/graaljs#1040 — a bug report, cited as behavioral evidence only].
4. graalvm.org documents the matrix: the optimizing runtime is "Supported" on Oracle GraalVM 25 and GraalVM CE 25 with no extra configuration, but "Oracle GraalVM implements additional optimizations performed during runtime compilation… for example, a more advanced inlining heuristic" — CE's in-image JIT is the lesser variant [P1: graalvm.org reference-manual/embed-languages, "Runtime Optimization Support"]. An interpreter-only fallback exists (`-Dtruffle.UseFallbackRuntime=true`) for when runtime compilation is unwanted [P1: same page].

### 9.1. What the in-image runtime JIT can do that pure AOT cannot

(Pure AOT here = Native Image *without* the embedded compiler: guest code runs interpreter-only via the fallback runtime [P1], or all Go code is lowered to host methods and frozen at build time.)

1. **Speculation + deoptimization on live guest behavior.** The embedded JIT speculates on observed receiver types, branch probabilities, and constant arguments at Go call sites and plants guards; on violation it deoptimizes to the interpreter and recompiles. Pure AOT has no deoptimization path and no speculation beyond frozen `--pgo` evidence (Oracle-only, §8). *Support: YES for guest code* [P1: HostCompilation.md; S: Protos Tier-2 validation].
2. **Continuous re-profiling and adaptive dispatch.** Inline caches and call-site profiles are re-observed for the life of the process; when the type mix shifts (§1's phase-change case) the JIT re-specializes without a rebuild or a new PGO training run. Pure AOT's profiles are build-time-frozen. *Support: YES — the standard Truffle compilation-trigger path, running inside the image.*
3. **Partial evaluation of the Go program itself.** PE derives optimized machine code from the guest ASTs — the mechanism behind every guest-level win in §§1–3. Without the embedded compiler there is no PE at all: pure AOT can only compile what the closed-world analysis saw as host code. *Support: YES* [P1: HostCompilation.md — "Guest compilation… uses Partial Evaluation and Futamura projections to derive optimized code from Truffle ASTs and bytecodes"].
4. **Late specialization of dynamically-shaped guest code.** New guest roots formed at run time (e.g., `reflect`-constructed call shapes, plugin-loaded Go code surfaced as new ASTs) can be compiled on demand rather than interpreted forever. *Support: in principle YES via the runtime-compilation pipeline; practical coverage for Go-specific shapes is [SPECULATIVE]* — falsify with `bench_reflect_dispatch`: interface calls through reflect-created values, hybrid vs pure-AOT; claim FALSE if hybrid ≤ pure-AOT.

### 9.2. What it cannot do in-image that it can on HotSpot

1. **Recompile or deoptimize AOT-compiled host code.** On HotSpot the interpreter itself is JIT-compiled and re-optimized as profiles evolve; in the image, host compilation "is applied ahead of time during native image generation" [P1: HostCompilation.md] — once, with build-time profiles only (`-H:TruffleHostInlining*` budgets). If a host-side shape goes stale in production (e.g., the interpreter's dispatch loop turns out megamorphic), there is no host recompilation; the guest compiler can only route around the frozen host.
2. **Compile arbitrary new host bytecode.** On HotSpot any loaded class can be JIT-compiled. In-image, runtime class loading (Crema, `-H:+RuntimeClassLoading`) plus JIT of runtime-loaded bytecode (`-H:+GraalJITCompileAtRuntime`) is *experimental* [P1: substratevm CHANGELOG GR-70601; runtime-class-loading.md], with documented limitations (no parallel class loading; methods removed by build-time analysis have no fallback and error at use) [P1]. For graalgo this bites at the Go↔Java interop boundary: dynamically-loaded Java on the host side stays interpreted-or-AOT, never newly optimized.
3. **HotSpot-grade code-cache management.** HotSpot sweeps, unloads, and re-tiers compiled code over long runs; SubstrateVM's in-image code management is younger and its long-run behavior under continuous re-profiling is [UNVERIFIED]. Falsify with `bench_longrun`: 24 h shifting workload tracking RSS and throughput drift; the "stable" claim is FALSE on monotonic RSS growth or >5% throughput decay.
4. **Oracle-only runtime optimizations.** The "additional optimizations performed during runtime compilation" (advanced inlining heuristic, better memory behavior) are Oracle GraalVM-only [P1: graalvm.org]. CE's in-image JIT is the weaker variant — peak-throughput claims for the drop-in (CE-buildable) story must be measured on CE, never extrapolated from Oracle numbers.

(What the image *does* give the JIT for free, retained from the prior draft: build-time-initialized heap — package init, stdlib tables, and runtime structures snapshotted at image-build time, removing init work from every process start [P1]; and closed-world devirtualization of monomorphic host-side calls, so the JIT spends its budget only on genuinely polymorphic guest sites.)

### 9.3. Cost model

No published clean delta for "embedding the compiler adds X MB" was found; every number below is labeled.

1. **Image size growth [ESTIMATE — not measured].** Two components: (a) the AOT-compiled Graal compiler + PE + optimizing runtime (a large Java codebase, compiled to native code *in* the image); (b) graph encodings + frame descriptors for every method marked runtime-compilable, retained in the image heap ("Runtime-compiled methods account for graph encodings in the heap" [P1: BuildOutput.md]). Order of magnitude: tens of MB on top of the application image [ESTIMATE — sized from the compiler being a multi-MB Java codebase, not from any measured image]. Falsifying measurement: build the same Truffle language image with and without the optimizing runtime (`-Dtruffle.UseFallbackRuntime=true`) and diff binary sizes; the estimate is FALSE if the delta lands outside 10–150 MB.
2. **Build time [S for plain images; hybrid delta ESTIMATE].** Plain Native Image builds are minutes-scale at GBs of RAM: ~5 min / 11.6 GB peak for a small Micronaut app [S: dev.to build log], 13m7s for a Spring Boot service [S: Baeldung build log]. Hybrid strictly adds the compiler to the closed-world analysis (more reachable methods to parse/compile) plus the graph-encoding retention pass — build time and peak build RAM grow, magnitude [UNVERIFIED]. Falsify with wall-clock `time native-image` and peak RSS, same input, with/without runtime compilation.
3. **Runtime memory [SPECULATIVE].** Resident costs beyond pure AOT: the embedded compiler's own code, compilation threads, the in-image code cache for guest compilations, AST retention for every runtime-compilable method (deopt/PE source), and deopt metadata. Expect RSS well above pure AOT; the honest comparison is against pure JIT on HotSpot (JVM heap + code cache + ASTs — same shape, different constants). Falsify with `/usr/bin/time -v` max-RSS on hello-world and a small HTTP server across all three modes; "hybrid RSS ≈ pure AOT" is FALSE if hybrid ≥ 2× pure AOT.
4. **Bounding knob.** `-H:MaxRuntimeCompileMethods` caps the runtime-compilable set (10,000 in Sulong's shipped config [S: oracle/graal#540, old]) — methods beyond the cap stay interpreted silently, a performance cliff to measure, not assume.

### 9.4. What breaks (adversarial)

1. **Closed-world correctness cliffs.** The runtime-compilable method set is computed once, at build time [P1: HostCompilation.md]. Anything the analysis cannot see — `reflect`-instantiated shapes, `plugin` packages, cgo-loaded symbols, guest code created after build — is not merely slow, it is *missing*: compilation requests for unregistered roots fail. Strictly worse than pure JIT, where the compilable set is open by construction. For Go, whose `reflect`/plugin story is more dynamic than Java's, computing a sound closed world is the single hardest build-time problem in this mode.
2. **Build-time vs live profile staleness.** Host inlining freezes build-time profiles (`-H:TruffleHostInlining*` budgets [P1: HostCompilation.md]); the guest JIT profiles live. When they disagree — the interpreter was host-optimized for a monomorphic dispatch shape that production violates — the host side cannot adapt, and the guest compiler burns deopt/recompile cycles working around a frozen host. Pure JIT re-optimizes both sides; pure AOT at least never promised adaptivity.
3. **Deopt-metadata bloat.** Every runtime-compilable method retains graph encodings + frame descriptors in the image, on top of the compiler itself (§9.3.1). This directly taxes the "small static binary" property that makes Go attractive — and unlike HotSpot, where metadata lives in a discardable code cache, here it is baked into the shipped artifact. Track via the build's "Runtime Compiled Methods" count [P1: BuildOutput.md]; do not assume it away.
4. **W^X / platform constraints.** Runtime code generation needs writable-executable memory; the in-image runtime-compilation path is one of the places SubstrateVM requests executable memory [S: iOS assessment 2026, carried from prior draft]. Hardened environments and some app-store policies forbid exactly this — a deployment veto pure AOT never faces.
5. **Build UX degradation.** Hybrid pays the Native Image build (minutes, GBs [S]) *plus* any PGO instrumentation run *plus* the embedded-compiler analysis — against `go build`'s seconds. Falsifying benchmark: wall-clock `time graalgo build` vs `time go build` on a mid-size module; if hybrid build ≥ 20× `go build`, the "drop-in" story needs a build-cache answer, not hand-waving.
6. **CE/Oracle split.** Peak claims measured on Oracle GraalVM do not transfer to the CE-buildable drop-in (§9.2.4) — benchmark the artifact you ship.

### 9.5. Falsifying benchmarks for hybrid claims (each claim dies by one)

1. "Hybrid beats pure AOT on shifting workloads" — `bench_phasechange` (§1b): hybrid vs pure-AOT(+PGO) vs pure-JIT. FALSE if pure-AOT(+PGO) ≥ hybrid steady-state, or if hybrid's recovery time ≥ pure-JIT's.
2. "Hybrid warms up faster than pure JIT" — `bench_warmup`: time-to-first-peak on a small HTTP server, hybrid vs pure-JIT. FALSE if within 20%. (Honest prior: hybrid *should* win here — no JVM bootstrap, build-time-initialized heap — but stay slower than pure AOT.)
3. "Hybrid matches pure-JIT peak" — `bench_peak`: long-run numeric + branchy mix, CE builds. FALSE if hybrid peak < 0.95× pure-JIT peak (frozen-host effects, §9.2.1, would show here).
4. "Hybrid startup ≈ pure AOT" — `bench_startup`: hello-world + small server time-to-first-response. FALSE if hybrid ≥ 1.5× pure-AOT (interpreter + runtime-init overhead).
5. "The complexity is worth it" — the meta-benchmark: geometric mean across 1–4 of (hybrid / best-of-both-single-modes), per workload class. **If hybrid never beats *both* single modes on any workload class, it is dominated and the mode is cut** — record that outcome explicitly rather than keeping three modes for marketing. The prior to beat: pure JIT already owns long-run peak, pure AOT already owns startup/footprint; hybrid must own at least one of {warmup, shifting-workload adaptivity, deployment-constrained peak} to survive.

## T6 key takeaways

1. Graal's famous speculation machinery mostly recovers static type info Go already has — the real, narrow wins are loop auto-vectorization (gc has none; GraalVM 25.3 added it), always-on runtime profiling (vs gc's opt-in PGO), and partial escape analysis past gc's flow-insensitive EA.
2. gc is a strong baseline: mid-stack inlining since 1.12, PGO inlining + devirtualization, good EA, excellent bounds-check elimination — every claimed win must beat gc *with* PGO, not the no-PGO default.
3. Valhalla is non-actionable: JEP 401 preview in JDK 28 (Aug 2026), still nullable, no flattened layouts — and Go's value semantics already capture most of its benefit; revisit 2028+.
4. Hybrid = the Graal compiler + Truffle PE AOT-compiled *into* the binary, compiling hot Go (guest) code at run time — real and shipping, primary-source verified (closed-world analysis computes the runtime-compilable method set; Protos validated guest compilation in a native executable, Sept 2026; CE's in-image JIT lacks Oracle-only runtime optimizations). It buys speculation+deopt and continuous re-profiling that pure AOT cannot have, but cannot recompile frozen host code the way HotSpot can; costs are tens-of-MB-scale image growth [ESTIMATE], minutes-scale builds, and deopt-metadata bloat, with closed-world correctness cliffs for reflect/plugin/cgo. Meta-benchmark stands: if hybrid never beats both single modes on any workload class, cut the mode.
5. Honest workload map: plausibly beats gc on vectorizable loops, shifting interface dispatch, partial-escape allocation shapes; matches on straight-line/PGO'd code; loses on startup, warmup, footprint, and anything crossing cgo/interop — the "optimizations NOT in gc" pitch is real but narrow, and every number above is [SPECULATIVE] until the named benchmarks run.
