## Findings

### 1. [BLOCKING] `toString` panics on typed-nil errors — new crash path in the diagnostic hot path
- **File:** `cmd/graalgo/testsynth.go:532-537` (new file numbering; `func toString` at :532, `case error:` at :536, `return x.Error()` at :537).
- **What:** the new `case error: return x.Error()` has no guard against a typed-nil error value — an interface holding a nil pointer whose `Error()` method dereferences its receiver (e.g. `*os.PathError`, `*os.SyscallError`, `*url.Error`, `*errors.errorString`, or any `func (e *MyErr) Error() string { return e.msg }`). Such values are routine: any function returning a typed nil as `error` (the classic Go gotcha), or a test passing a concrete `*os.PathError` variable, flows through `t.Errorf`/`t.Logf("%v", err)` into `toString`. The old code returned `"<value>"` for errors and could never panic here; this diff introduces the panic.
- **Consequence:** the panic unwinds to the test's deferred recover and is reported as a user panic. For `Errorf` the verdict stays FAIL but the diagnostic is destroyed (a confusing `panic: runtime error` line instead of the values); for `Log`/`Logf` in an otherwise passing test it is a spurious FAIL. A test driver whose job is faithful reporting must not crash on the values it is asked to print.
- **Remediation:** guard the `Error()` call so `toString` is total over error values, e.g.:
  ```go
  case error:
      return errorString(x)
  ```
  with a helper in the shim template:
  ```go
  // errorString renders an error value; a typed-nil error whose Error
  // method panics renders as "<nil>" instead of crashing the diagnostic.
  func errorString(err error) (s string) {
      defer func() {
          if r := recover(); r != nil {
              s = "<nil>"
          }
      }()
      return err.Error()
  }
  ```
  Add a test driving `t.Logf("%v", (*os.PathError)(nil))` (or a typed-nil custom error) through the synthesized driver and asserting the test still passes and the output contains `<nil>` rather than a panic line.

### 2. [BLOCKING] `runCleanups` silently drops cleanups registered by cleanups — deviates from `testing` semantics
- **File:** `cmd/graalgo/testsynth.go:237-251` (new file numbering; `func (t *graalgoT) runCleanups` at :237; list captured once at :238, drained at :240).
- **What:** the list is captured once (`cleanups := t.cleanups; t.cleanups = nil`) and drained a single pass. A cleanup registered by another cleanup during that pass is appended to the fresh list and never runs. Real `testing` runs cleanups registered during cleanup execution (its cleanup loop drains until empty). The comment above the function misdescribes this as idempotency ("a second call (e.g. a cleanup registered by another cleanup) is a no-op for already-run entries") — the registered-by-cleanup function is not run at all, and no second call ever happens.
- **Remediation:** drain until empty:
  ```go
  func (t *graalgoT) runCleanups() {
      for len(t.cleanups) > 0 {
          cleanups := t.cleanups
          t.cleanups = nil
          for i := len(cleanups) - 1; i >= 0; i-- {
              // existing per-cleanup body with recover
          }
      }
      if t.ctxCancel != nil {
          t.ctxCancel()
          t.ctxCancel = nil
      }
  }
  ```
  Correct the comment to state that cleanups registered by cleanups run too. Add a test: a cleanup that registers a second cleanup, asserting both ran (in the synthesized driver, end-to-end).
