### FE-01 — NodeFactoryV2 silently miscompiles multi-value assignments, declarations, and returns — P1
- **Files:** `internal/backend/truffle/src/main/java/graalgo/frontend/v2/NodeFactoryV2.java:329-353,456-557,559-619`.
- **What:** (a) Return: the multi-result branch's own comment says "build a block that evaluates all, return first" but the code just does `return new ReturnNode(built.get(0))` — results 2..n are built but never evaluated, so their side effects are silently dropped. (b) Assign: `a, b = b, a` is built as sequential `AssignNode`s, and `AssignNode.executeVoid` evaluates its RHS at execution time, so the swap reads the already-overwritten `a` — both end up as old `b`. `a, b = f()` assigns the *same* call node to both LHSs, so `f()` executes twice and both get the first result. (c) VarDecl: the loop `for i < values.size() && i < names.size()` means `var a, b = f()` assigns only `a`; `b` silently stays zero. There is no tuple/multi-value mechanism anywhere in v2. Verified by the reviewer reading the code this run.
- **Suggested fix:** needs design — introduce temp slots / a multi-value carrier in the factory (mirror how v1 `NodeFactory` destructures multi-value calls), and fail loudly on multi-value forms until that lands.
- **Lane:** V2-A.

### FE-02 — NodeFactoryV2 has no function resolution — calls to any named function fail loudly; its "All emitter kinds are implemented" claim is false — P1
- **Files:** `NodeFactoryV2.java:69-78` (class javadoc) vs `buildFunction :254-300`, `buildIdent :~1030-1050`.
- **What:** the factory never registers functions in any callable table, and `buildIdent` resolves every ident through `scope.slotForObj`, which throws for func objects (functions are never declared as slots). So `main` calling a same-package helper, or any recursion, throws `FrontendException: object id N not declared in scope` at build time. The only callable things are builtins and func-typed variables.
- **Suggested fix:** needs design — build a function table in `buildProgram` (name/id → `V2Function`/call target) and resolve call idents through it instead of frame slots; correct the javadoc.
- **Lane:** V2-A.

### FE-03 — NodeFactoryV2 silently drops the Document's `globals` and method receivers — P1

### FE-04 — NodeFactoryV2 hardcodes wrong node-construction arguments: `append`/`copy`/`new`/`make`/composite literals/`print` — P1 (silent miscompilation)
- **Files:** `NodeFactoryV2.java:1076-1132,1285-1287,662-663`.
- **What:** (a) `append` passes `elemKind = INTERFACE` always (:1084); `AppendNode` uses elemKind for element reads, `growslice` element size, and `elemHasPointers`, so `append([]int{1}, 2)` grows/copies with the wrong element size. (b) `copy` passes INTERFACE (:1132) into `Intrinsics.slicecopy`. (c) `new` builds `new NewNode(GoKind.POINTER, null)` (:1102) — elemKind must be the *referent's* kind (`NewNode` allocates via `freshZero(elemKind, …)`), so `new(int)` allocates a pointer-typed zero. (d) `make` slice form passes INTERFACE (:1088-1099) into `Intrinsics.makeslice` — currently latent, since the emitter cannot emit a `make` type arg at all (FE-05). (e) `buildCompositeLit` passes `elemKind=INTERFACE`, `keyKind=INT64`, `arrayLen=-1`, `structDesc=null` (:1285-1287): `[]int{1,2,3}` allocates via `Boxing.newArray(INTERFACE, …)`; `[3]int{…}` calls `newArray(elemKind, -1)`; `Point{…}` NPEs at `structDesc.longsCount()` (`CompositeLitNode.java:138`); `map[string]int{…}` boxes string keys via `MapKeys.box(INT64, …)`. (f) `print`/`println` returns `args.get(0)` only (:1113-1121) despite the comment "evaluate args for side effects" — args 2..n are never evaluated. (g) `buildRange` hardcodes `keyBoxed=false, valueBoxed=false` (:662-663) where v1 computes per-variable boxed-ness (`NodeFactory.java:5512`); wrong for captured/address-taken range variables.
- **Suggested fix:** derive elem/key kinds from the type table (the emitter already provides them via `fields["type"]`), derive `arrayLen` from the array type, build a `GoStructDescriptor` for struct literals (as v1 does), evaluate all print args (e.g. a block of `ExprStmtNode`s), and compute boxed-ness per range variable.
- **Lane:** V2-A.

### BE-01 — `GoChan.trySend`/`tryRecv` buffer past a self-claimed select waiter — lost wakeup / value misordering — P1
- **Files:** `internal/backend/runtime/src/main/java/graalgo/runtime/GoChan.java:232-248` (`trySend`), `:261-275` (`tryRecv`).
- **What:** `pollAccepting` skips a self-claimed select waiter and returns `RETRY_WAIT`, but `trySend` then takes the buffered completion anyway (`if (count < buf.length) { buf[tail] = v; ... return SENT; }`) instead of returning `RETRY`; `tryRecv` likewise takes from the buffer (`if (count > 0)`) past a self-claimed select sender. The comment blesses this ("the waiter belongs to a select completing elsewhere") — that rationale is wrong for the common case: a self-claimed waiter belongs to a selector *mid-sweep* on another channel, which has not decided anything yet and will park on this waiter. The selector's sweep does not re-poll before parking (`SelectOp.java:307-315`), so the buffered value wakes nobody: the select sleeps until an unrelated event (or the deadlock detector, which does not exist — see BE-04). When it finally wakes, it gets the *second* value while the first sits in the buffer (gc delivers the first; gc never buffers past a waiting receiver — `chan.go` checks recvq/sendq before the buffer). A `close()` in between is worse: the select gets `(zero, false)` while a buffered value exists, violating gc's drain-then-EOF order. Verified by the reviewer reading `trySend` this run; the sweep/park mechanism needs re-verification by the lane. Use the truffle skill for backend work.
- **Suggested fix:** when `pollAccepting` returns `RETRY_WAIT`, return `RETRY` (never complete past a self-claimed waiter) — the existing RETRY retry loops in `send()`/`recv()`/`SelectOp.tryCompleteReady`/`completeUnderLock` already handle it. This changes the documented design decision in the `trySend` comment, so re-verify the CI-41943236460 lost-wakeup case still holds after the change.
- **Lane:** BE-01.

### BE-02 — `TlsRuntime.unwrap` discards app bytes already produced in the same call when a close_notify follows — P1
- **File:** `internal/backend/interop/src/main/java/graalgo/p3tls/TlsRuntime.java:576` (`if (res.getStatus() == SSLEngineResult.Status.CLOSED) { return null; }`).
- **What:** the unwrap loop drains each record's plaintext into `out`, then on a `CLOSED` record returns `null` immediately, throwing `out` away and skipping the `PENDING` save. Use the truffle skill for backend work.
- **Suggested fix:** on `CLOSED`, return the accumulated `out` bytes if non-empty (and stash remaining input to `PENDING`); return `null` only when no app bytes were produced in this call.
- **Lane:** TLS.
