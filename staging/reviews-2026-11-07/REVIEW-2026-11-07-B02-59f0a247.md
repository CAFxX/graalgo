## 1. Correctness — mechanism traced end to end

- `--` parsing (`Main.run`): after `--`, every token is positional — the first
  is the input file, the rest are the program's args; in `--batch` mode every
  token after `--` is a (rejected) program argument. Flags after `--`
  (`--check`, `--dump-vars`, …) are program args, not launcher flags.
  `--batch=file -- x` → usage error exit 1; `--batch` with empty file errors
  before the program-args check (correct order). `file.go -- -- x` →
  program args `["--", "x"]` (documented contract: everything after the first
  `--` is program args). Pre-existing behaviour untouched: a bare second file
  is still "too many input files", unknown `-x` flags still usage errors.
- Init placement (`Main.runOne`): `initializeOsSurface(buildGoArgv(...))` runs
  after frontend + AST build and before `program.root().call()` — i.e. before
  any Go code runs, including package-var initializers. `--check` returns
  before init (correct: no execution, no surface needed). `--dump-vars` and
  `--dump-polymorphism` paths execute after init. `runOne` has exactly two
  callers (`run`, `runBatch`); batch calls it once per entry with empty
  program args, so each entry gets a fresh surface.
- `buildGoArgv`: `argv[0]` = absolute, normalized entry-point path;
  `argv[1:]` = program args verbatim.
- Provider (`GoOsSurfaceInitializer.initialize` → `GoOs.init` →
  `GoOs.resetState`): full reset — `HANDLES` cleared and stdio cookies 1/2/3
  re-registered, `NEXT_COOKIE` reset to 16, `ENV_OVERLAY`/`ENV_REMOVED`
  cleared, `ENV_CLEARED=false`, `ARGV` cloned from the argument, `VCWD`
  reset to the process cwd, UnixSystem re-probed. No env/argv/vcwd/stdio-cookie
  state can leak from batch entry N into entry N+1.
- `os.Args` wiring (verified, not assumed): synthetic `os`
  (`internal/frontend/synth_os.go:309-318`) declares
  `var Args = __initArgs()`, which reads the `osArgc`/`osArgv` linkname
  intrinsics bound to `GoOs.argc`/`argv`, which read the static `ARGV` set by
  `GoOs.init`. The `Main.java` comment naming `synth_os.go __initArgs` is
  accurate. Package-var init runs during `program.root().call()`, after init.
- The sync launcher already called `GoOs.init` directly
  (`P3SyncMain.java:515`); the plain launcher was the remaining gap. B-02
  closes it with a ServiceLoader provider because the launcher module cannot
  compile-depend on interop (circular). Consistent with the pre-existing
  `WireKindRegistrar` shape.
- No-provider path: warns once per JVM on stderr ("no OsSurfaceInitializer
  provider … os.Args will be empty") instead of failing silently. The provider
  is registered in the real build (service file + compiled interop), so this
  is a misconfiguration alarm, not a silent fallback. The `static boolean`
  warn-once flag is fine on the single-threaded launcher path.
- Net state: `GoOsSurfaceInitializer` javadoc explicitly states net state is
  NOT reset here and belongs to B-04. Scoped and documented, not a silent gap.
- gc ground truth (probed directly with `go` 1.27.1, not from memory):
  `go run prog.go -- alpha beta` → `argv[0]` is an absolute temp-binary path
  and `--` is passed through as a program arg (`os.Args=[exe,--,alpha,beta]`);
  `go run -- prog.go x` → `argv[0]` absolute, args `[x]`. Graalgo-run consumes
  `--` as its launcher separator (it has its own flags to disambiguate), which
  is a deliberate, documented divergence from `go run`'s passthrough — and the
  differential corpus compares built-binary invocations
  (`10_args.go.args` = `hello world 123`), where the shapes agree. The
  absolute-`argv[0]` rule matches gc's built-binary absolute path.
  No test asserts wrong gc behaviour.

## 2. Generality / bridges — none found

- New `OsSurfaceInitializer` interface + ServiceLoader discovery: a general
  mechanism, same shape as `WireKindRegistrar`. No new synthetic stdlib
  (`synth_os.go` pre-exists and is untouched by this commit), no import-overlay
  allow-list, no package-name-keyed conditional, no Java reimplementation of
  stdlib behaviour — the provider forwards to the existing `GoOs` surface.
- `ServiceLoader.load` per `runOne` call instantiates a fresh, stateless
  provider per entry; only one provider is registered (a second would also
  init, last-wins on `ARGV` — not a defect at one provider).
